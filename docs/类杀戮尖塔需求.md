# 类杀戮尖塔（Slay the Spire 类）需求分析与实现指南

> 文章面向两名仅有 C/Python 基础、无项目管理经验的软工大学生，在小周期内协同开发一款「类杀戮尖塔」卡牌构筑肉鸽。
> **特别说明**：你们已有一个「杀戮尖塔人物 mod」作为基础。这份文档最核心的一步是帮你分清两件事——
> **① modemod 已经给了你什么（内容/数据/数值/美术）**，**② 你还必须自己实现什么（游戏引擎 / 战斗机制 / 结算逻辑）**。
> 请先读完第 1 节再往下看，否则很容易误判工作量。

---

## 0. 一句话定义我们要做什么

一款**回合制、卡牌构筑、爬塔式肉鸽**游戏。玩家从牌组开始，沿随机生成的地图节点前进；每个节点可能是战斗、精英、营地、商店、宝箱或事件。战斗中用有限的「能量」打出手牌，击败敌人后获得新卡牌或金币，逐步构筑自己的牌组，挑战越来越强的敌人，最终通关。

核心体验三要素：
- **构筑感**：每局牌组都不一样，靠选卡、升级、删卡、遗物组合出强套路。
- **肉鸽感**：地图、敌人、奖励、事件随机，死了就重开，重开有新体验。
- **策略感**：回合制的抽卡/能量/费用/状态管理，考验规划而非反应速度。

## 1. 最关键的认知：mod 给了你什么，没给你什么

「人物 mod」本质上是一个**内容包**，它依赖原版游戏的完整引擎才能运行。你拿到手的通常是卡片、遗物、敌人等**定义数据/资源**，但**引擎本体必须自己写**。

### 1.1 mod 大概率已经给你（可以直接复用的资产）

| 资产 | 说明 | 你的复用方式 |
| --- | --- | --- |
| **卡牌定义** | 名称、费用、类型（攻击/技能/能力）、效果描述 | 作为设计参照，转成你自己的数据格式 |
| **遗物定义** | 遗物效果、触发时机 | 同上 |
| **卡牌美术/图标** | 卡面图、图标 | 直接当素材用（注意版权，见 6.4） |
| **数值/平衡信息** | 各卡牌伤害、费用、稀有度 | 极宝贵的设计与调参参照 |
| **关键字/状态系统** | 弱化、易伤、中毒、力量等 | 理解其规则并重新实现 |

### 1.2 mod 大概率**没有**给你（你必须自己实现）

| 缺失部分 | 说明 | 难度 |
| --- | --- | --- |
| **战斗引擎** | 出牌、能量、手牌、弃牌、抽牌、结算 | 高（核心） |
| **地图系统** | 随机节点生成、路径选择、节点类型 | 中 |
| **敌人 AI & 意图系统** | 敌人每回合要干什么、意图显示 | 中高 |
| **状态/关键字结算引擎** | Weak/Vulnerable/Strength/Poison 等如何叠加生效 | 高（最易出错） |
| **奖励系统** | 战斗后 3 选 1、金币、遗物、药水 | 中 |
| **商店/营地/事件** | 交互界面与规则 | 中 |
| **存档系统** | 保存/读档、重开 | 中 |
| **UI 与交互** | 卡牌拖拽、点选、意图、伤害数字 | 高（工作量最大且耗视觉） |
| **美术整合与特效** | 敌人图、卡面、动画、音效 | 中 |

> 结论：**mod 是"内容仓库 + 设计教科书"，不是"引擎"**。你实际要写的是一个真正的卡牌跑酷引擎。这会决定你的工期预期。

## 2. 核心系统清单（必须实现的模块）

把游戏拆成以下几个模块，每人都可以领一个或多个独立实现。

### 2.1 战斗系统（心脏）
- 回合结构：回合开始 → 抽牌 → 玩家行动 → 敌人行动 → 回合结算。
- **牌组三态**：抽牌堆、手牌、弃牌堆（打出的牌进弃牌堆，抽牌堆空时把弃牌堆洗回）。
- **能量系统**：每回合固定能量（如 3 点），出牌消耗能量；能量不足的牌不可打。
- **手牌上限**（如 10），超出需弃牌。
- **目标选择**：多敌人时选择攻击目标；技能通常不需目标。

### 2.2 卡牌系统（内容核心）
按类型分：
- **攻击牌**：造成伤害，受「力量」「易伤」影响。
- **技能牌**：格挡、抽牌、减益等。
- **能力牌**：本战斗内持续生效的 buff。

按费用分：0 费、1 费、2 费、3 费，以及 **X 费**（可自由投入能量，如"X 费：造成 X 点伤害"）。

卡牌属性字段（建议数据结构化）：
```
{
  名称, 费用, 类型(攻击/技能/能力), 稀有度(普通/罕见/稀有),
  目标(单个敌人/所有敌人/自身/无),
  伤害, 格挡, 抽牌数, 施加状态(类型+层数),
  关键字(消耗、保留、固有等), 升级后效果
}
```

### 2.3 状态/关键字系统（隐藏的坑王）
这是整个游戏**最容易写出 bug**、也最难改的地方。需要一种通用的「效果描述 → 实际结算」机制。常见状态：

| 状态 | 效果 | 关注点 |
| --- | --- | --- |
| 力量(Strength) | 每次攻击追加伤害 | 攻防结算顺序 |
| 敏捷(Dexterity) | 每次格挡追加 | 同上 |
| 易伤(Vulnerable) | 受到攻击伤害 +50% | 乘算时机 |
| 弱化(Weak) | 造成的攻击伤害 -25% | 乘算时机 |
| 中毒(Poison) | 每回合扣血并递减 | 层数与每回合减伤 |
| 格挡(Block) | 本回合减伤，回合末清空 | 清空时机 |

> 建议：一开始别做花样，先把 **力量/敏捷/易伤/弱化/格挡/中毒** 这 6 个最基础的做对，跑通全部交互，再逐步扩展。

### 2.4 敌人系统 + 意图显示
- 敌人有：生命值、行动模式（多套技能循环或随机）、每回合头顶显示「意图」。
- **意图**：告诉玩家敌人下回合要攻击(几点)、格挡、加 buff 还是 buff 自己。这是玩家做决策的依据，必须显示。
- 敌人分级：普通敌人、精英、Boss，数值和行动复杂度递增。
- Boss 通常有「行动序列表」，按固定顺序出招。

### 2.5 地图系统（爬塔）
- 自上而下的节点图，玩家只能相邻选择前进。
- 节点类型：战斗、精英、营地、商店、宝箱、事件、Boss。
- 随机生成：每层不同，保证一定可玩性（别生成死路）。
- **营地**：休息（回血）或升级卡牌（二选一），是构筑的关键节点。

### 2.6 奖励系统
- 战斗胜利后：**从 3 张随机卡里选 1**（或跳过），并发金币。
- 精英战：额外掉遗物。
- 商店：花钱买卡、遗物、药水、删除卡牌（删卡是构筑很重要的一环）。
- 事件：二选一/有代价的抉择，提供肉鸽变数。

### 2.7 遗物系统（可选进阶）
- 被动永久加成：如"每场战斗开局多抽 1 张""首次格挡+X"。
- 触发时机要设计：战斗开始、回合开始、打出特定牌、敌人死亡等。
- 遗物是构筑深度的重要来源，但也**显著增加测试面**，可放到 MVP 第二阶段。

### 2.8 药水系统（可选）
- 单次消耗品，如"造成 10 点伤害""抽 2 张牌"。
- 优先级可放最末，MVP 可砍掉。

### 2.9 存档系统
- 保存：当前楼层、节点位置、牌组、金币、生命、遗物、药水。
- 至少支持「退出重进继续」和「重开一局」。

## 3. 需求优先级：MVP 和「想要」

把需求按「必须 vs 可以砍」分层，避免工期失控。**小学期大概率做不完完整版**，先保证核心循环可玩。

### 🟢 MVP（第一优先级，先做这个，保证能玩）
1. 一个战斗场景：抽牌、出牌、能量、弃牌、回合切换。
2. 基础卡牌约 8~12 张（两类卡：攻击 + 技能，含基础的伤害/格挡/抽牌）。
3. 常见状态：力量、敏捷、易伤、弱化、格挡（5 个即可）。
4. 单次遭遇：1 个敌人 + 意图显示 + 胜利/失败结算。
5. 基础 UI：卡牌显示、手牌、点击出牌、目标选择、伤害数字。
6. 一回合内完整的「抽牌-出牌-敌人行动-结算」循环。

### 🟡 第二阶段（在 MVP 稳定后可加）
7. 地图系统 + 多节点选择 + 营地（回血/升级）二选一。
8. 奖励系统：战后 3 选 1 加卡。
9. 2~3 种敌人的卡片池，精英战。
10. 卡牌升级（Smith）系统。
11. 商店 + 金币。
12. 存读档。

### 🔴 第三阶段（有富余才做，否则直接砍）
13. 遗物系统。
14. 药水系统。
15. 事件系统。
16. Boss 战 / 多楼层 / 通关动画。
17. 复杂关键字（消耗、保留、固有、X 费、多段）。
18. 音效、动画特效、精美美术。
19. 进阶难度（如"允许敌人多动""敌人会变强"）。

> **强烈建议**：先把 MVP 打通做顺，再逐层加。不要一上来就铺全功能。

## 4. 技术实现建议（结合 C/Python 基础）

### 4.1 语言与框架选择
你们只有 C/Python 基础，**最推荐直接上 Python + 一个图形库**，避免额外学引擎。

| 方案 | 优点 | 缺点 | 推荐度 |
| --- | --- | --- | --- |
| **Python + Pygame** | 入门快、与你基础契合、生态成熟、够用 | 中大幅 UI/动画较费手写 | ⭐⭐⭐ 推荐 |
| **Python + 命令行(文本版)** | 最快打通核心逻辑，先做"逻辑版" | 无视觉，展示差 | ⭐⭐(先做原型) |
| **Godot** | 免费、2D 强、有场景/动画编辑器 | 需学新语言/引擎，时间成本高 | ⭐⭐ |
| **Unity + C#** | 成熟、资源多 | 需学 C# 和庞大引擎 | ⭐(不推荐短期) |

**建议策略**：**先用纯 Python 把战斗逻辑做成"文本/命令行可玩"的版本**（核心逻辑不依赖图形），等逻辑稳定后再套一层 Pygame 的 UI。这样能最大化复用，且逻辑和显示分离，便于两人并行。

### 4.2 数据驱动设计（最重要的一条原则）
**卡牌、敌人、遗物、状态都不要写死在代码里，而是用数据（如 JSON/字典/列表）描述，用一个"解释器"去读。**

```python
# card 数据示例
CARD = {
    "name": "打击",
    "cost": 1,
    "type": "attack",
    "rarity": "basic",
    "effect": {"damage": 6, "target": "single"},
    "upgrade": {"damage": 9},
}
```
这样做的好处：
- 现在用 mod 里的卡牌定义，**改数据即可变成你的卡**，不用重写逻辑。
- 加新卡 = 加一条数据，工作量极小。
- 便于平衡调参。
- 两人可分工：一人写引擎，一人填数据。

### 4.3 模块划分（两人并行）
| 成员 | 负责模块 |
| --- | --- |
| A | 战斗引擎、回合状态机、卡牌结算、状态系统 |
| B | UI 交互、地图系统、奖励/商店/营地、美术整合 |

> 关键：**先一起定好数据格式和接口约定**（卡牌/敌人/状态的数据字段、事件接口），再各自开发，最后对接。这是没项目经验时最容易踩的坑。

### 4.4 架构建议
- **状态机**：战斗内用状态机管理（`PlayerTurn → EnemyTurn → RoundEnd`）。
- **实体-数据分离**：把"卡牌效果"抽象成可组合的小函数/规则，而不是每个牌写一套 if。
- **面向对象 + 数据驱动结合**：卡牌/敌人/遗物做成类，属性来自数据。
- **写测试**：哪怕 console 输出验证也行。卡牌肉鸽的 bug 往往是"两张牌交互时数值不对"，用最小的单元验证能救你。

## 6. 必须提前想清楚的风险（这几点决定成败）

### 6.1 卡牌交互的"组合爆炸"
卡牌肉鸽最难的不是单张卡，而是**卡牌 × 状态 × 遗物**组合时的 bug。**协议先行**：先定义好通用的效果描述规则（如"施加易伤 2 层"的格式），所有卡都用这个格式，避免每张卡一个特例。

### 6.2 数值平衡
- 开局第一场战斗必须能赢、不至于太轻松。
- 敌人强度要随节点递进。
- 调参靠"多打几十局"来感觉，建议你们自己先玩个几十局再定卡。
- **借用 mod 的数值**会是极大的起点优势，别浪费。

### 6.3 时间与范围失控（最大风险）
- 新手最常见的死法：**做了一大堆"想要"，但核心循环没跑通**。
- 严格执行 MVP，先把一场战斗做顺，再谈地图和遗物。
- 定期演示：每完成一个里程碑就互相演示，确认方向没偏。

### 6.4 版权与资源（mod 复用注意）
- 从 mod 提取的**美术素材/卡图**，若是他人受版权保护的作品，用于"课堂作业"尚可，但**不要公开发布/商业使用**。
- **机制与规则不受版权限制**，所以你可以完全按原版规则设计自己的卡、自己画图。
- 最稳妥：**参考 mod 的数值和规则，用你自己的方式重画卡面**。名字和效果可参考，图尽量自己画或找免费素材。

### 6.5 目标选择与交互的复杂
多敌人时点选目标、以及"选择目标才能出牌"这类交互，是 UI 里很繁琐的部分。建议先做「个敌人」场景；多敌人时给"默认当前目标 + 点击切换"。

## 8. 一句话总结给两位

> 你们手里的是「内容」，不是「引擎」。真正的工作是**先写一个最小的、能跑通"抽牌→出牌→敌人行动→结算"的战斗引擎（文本版即可）**，把基础状态和 8~12 张卡做对，再套 UI、加地图和奖励，最后再做遗物和深度。**每做完一个能玩的里程碑就互相演示，别贪多。** mod 的数值和卡牌规则是你们的宝库，用它省下大量设计时间，但别被它的完整度吓到——你只需要先做最核心的一小部分。
